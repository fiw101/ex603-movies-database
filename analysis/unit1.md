## Unit 1 Analysis

<b>Modelling justification, 400 to 600 words. Cover your key design decisions: your choice of primary keys, your ON DELETE behaviors, and which rules you chose to enforce in the schema rather than leaving to the application.</b>

The movie rating database is used to store data on users, movies, ratings, genres, as well as the relationship between movies and genres. The goal is to utilize this to analyze the movie ratings. The database also uses the integrity constraints to make sure only valid data is stored.

The primary key in every entity needs to be unique and non NULL because it is used to distinguish each record. The primary key in the users table is user_id so that each user is able to be identified in the platform. The movie_id is the primary key in the movies table which can be used to identify the movie, in case multiple movies have the same title. The primary key for the ratings table is rating_id to identify a single rating because users can have the same score for each movie. The genre_id is the primary key for the genres table to help identify each genre and avoid two genres having the same ID. For the movies_genres junction table, the movie_id and genre_id form a composite primary key since a movie can belong to many genres and a genre can be applied to many movies. A composite primary key ensures the relationship for each movie and genre is unique. 

The foreign key relationships are very important because they are used to maintain referential integrity between the tables. I choose ON DELETE SET NULL for the user_id foreign key in the ratings table because if a user is deleted, their ratings would still be considered useful, since this is a database focused on movie ratings. For the movie_id foreign key in the ratings table, I choose ON DELETE RESTRICT which prevents deleting a movie that has ratings and preserves rating history. Instead of deleting a movie, the is_active flag in the movies table can be set to false. For genre_id in movies_genres, I choose ON DELETE RESTRICT to help prevent accidental deletion of important genres that would affect the genres associated with multiple movies. For movie_id in movies_genres, I choose ON DELETE RESTRICT because instead of deleting a movie, the is_active flag should be used. These rules help to keep the database clean and organized by removing records that are no longer needed. 

Another key design decision is the relationship cardinalities. For example, users have a one to many relationship with ratings since a user can have many ratings. There is also a one to many relationship between movies and ratings since a movie can have many ratings. Movies and genres have a many to many relationship (N:M) indicated with the junction table called Movies_Genres because each movie can be classified under multiple genres and each genre can have many movies associated with it.

There are several rules needed to enforce in the schema. For example, the primary key needs to be unique and non NULL to prevent duplicate records. The duration_minutes attribute in movies must be an integer greater than 0 because a movie cannot have a negative movie length. The score must range from 1 to 5 to prevent users giving the invalid rating. The year released and datetime reviewed need to follow the correct year and datetime format respectively. Moreover, if an active movie needed to be still searchable so the users can give the ratings. All of these constraints make the database more reliable and avoid invalid data.

<b>Reflection, 150 to 250 words. Your ERD encodes decisions the requirements left open. Name one decision you made that a different designer could reasonably have made differently, and defend your choice in terms of the read and write patterns the platform will face.</b>

One design decision I made was choosing ON DELETE SET NULL for the user_id foreign key in the ratings table because ratings are useful information for a movie rating database and should be preserved even if a user needs to be removed. When a user is deleted, the user_id becomes NULL but the rating, movie, score, and date reviewed are still kept in the database. By doing so, the database system can use their rating to calculate average scores and analyze any preference.

Another designer could potentially choose ON DELETE CASCADE, which would mean that when a user is deleted, the user’s ratings are also deleted because those should belong to that user. The benefit to this would be that this keeps the database clean. However, this also means some useful rating records would be removed when a user is deleted. Since the main purpose of this database is to analyze movie ratings, ratings seems like a crucial part of the data, so I choose to keep the rating data but still allow users to be able to delete their accounts.
